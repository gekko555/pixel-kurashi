# 02_設計判断（確定事項）
| 項目 | 決定内容 | 理由 |
| --- | --- | --- |
| 認証方式 | Spring Security + サーバーセッション(Cookie) | 最も標準的で学習価値が高い |
| パスワード | BCryptでハッシュ化（平文NG） | ソルト内蔵の一方向ハッシュで安全 |
| ログインID | username のみ（メール等の個人情報なし） | 保持する個人情報を最小化しリスク低減 |
| money_record紐付け | user_idを今回追加 | 将来のホーム集計「自分の収支」に必須 |
| CSRF | 初期は無効化 | まず認証フローを動かすことに集中 |

# 08_セキュリティ観点（今回含める）
| 観点 | 対応内容 |
| --- | --- |
| 入力バリデーション | username: 3-20文字・半角英数, password: 8-72文字 |
| 例外ハンドラ | バリデーション=400, 重複=409, 想定外=500（詳細はログのみ） |
| ユーザー列挙対策 | ログイン失敗は「ユーザー名またはパスワードが正しくありません」で統一 |
| 機密情報保護 | passwordはレスポンス・ログに出さない |
| 現在ユーザー取得 | SecurityContextHolderからusername取得しuser_idに反映 |

# 12_学習メモ
| 用語 | 説明 |
| --- | --- |
| BCrypt | ソルト内蔵の一方向ハッシュ。同じパスワードでも毎回違うハッシュ |
| UserDetailsService | ログイン時にDBからユーザーを引くための窓口 |
| SecurityContextHolder | 現在の認証情報を保持。Service層で「今のユーザー」を取得 |
| セッション認証 | ログイン成功でサーバーがセッション作成、Cookie(JSESSIONID)で識別 |
| CORS + credentials | フロントが別ポート(5173)のためCookie送受信に両側設定が必要 |
